# OpenFit health-agent foundation audit

**Evidence baseline:** `main` / `dd69073ddbf1cafdb38658bd2fb045221c8ce00a` (audited 2026-07-12)

## Purpose and classification

This audit compares the repository as it exists at the evidence baseline with the Wayfinder destination: an Expo app with equivalent iOS, Android, and web coaching capabilities; Google identity; a per-user Cloudflare Agent/Durable Object; persistent, deletable Coach Conversations and an editable Coach Profile; safe health-data coaching; and user-correctable nutrition logging into Google Health from text, manual form, photo, barcode, receipt, and ElevenLabs voice. Google Health is canonical, OpenFit may mutate only ledger-owned entries, consumption must be clear before a write, estimates must be marked, and exercise writes are outside the MVP.

Classifications mean:

- **Trustworthy foundation** — implemented, connected to the current app, and suitable to retain, although production verification may still be needed.
- **Prototype** — meaningful implementation exists, but it is disconnected, weakly secured, unverified, or materially incomplete for the destination.
- **Gap** — destination behavior is not present.
- **Contradiction** — current behavior or product copy conflicts with the destination or another implemented subsystem.

No runtime secrets, OAuth tokens, or user health records were inspected or included. Source code and checked-in configuration are the primary evidence; README and store material are used only as product/deployment evidence.

## Executive finding

The repository contains two largely disconnected foundations:

1. A source-complete Expo SDK 56 health dashboard that signs in with Google, reads Google Health directly from the client, caches health snapshots in memory, persists tokens locally, updates native widgets, and can manually export three record classes to Apple Health on iOS. Static checks pass, but this audit did not establish live runtime behavior.
2. A compile-clean Cloudflare Worker Agent prototype with a per-name SQLite Durable Object, encrypted Google refresh-token state, Google Health reads and writes, an ownership ledger, and a single-turn Workers AI question endpoint.

The first is the strongest product/UI foundation. The second is a useful ownership and mutation prototype. Neither is currently a Personal Health-Data Coach: the app never calls the Worker, there is no user-scoped server identity, no conversation/profile model, no nutrition capture or estimation pipeline, no persistent messages, and no behavioral or integration tests. The checked-in privacy policy describes only the client-side dashboard architecture and directly conflicts with the Worker’s durable token/ledger storage and AI processing.

## Foundation worth carrying forward

1. **Expo SDK 56 shared UI and native-build setup.** It is current, strict-typed, and already supports iOS, Android, and server-rendered web.
2. **Google Health read normalization and metric catalog.** It provides working dashboard context and demonstrates pagination/rollup patterns.
3. **Two idempotency precedents.** The Worker’s Google ownership ledger is the relevant canonical-write base; the local Apple Health ledger is a useful separate example.
4. **Durable Object + encrypted refresh-token prototype.** It establishes the intended Cloudflare topology, but not production tenancy/authentication.
5. **Consistent non-clinical product language.** The app, terms, privacy page, and store drafts already frame OpenFit as wellness rather than medicine.

## Critical path exposed by the audit

1. Define and implement verified Google user identity, a server session, and deterministic subject-to-Durable-Object routing.
2. Choose one Google OAuth/token-custody architecture and integrate the Expo app with the Worker; remove the duplicated/coarse authorization path.
3. Establish explicit Durable Object schemas and deletion/retention contracts for Coach Conversation, Coach Profile, and the OpenFit-owned nutrition ledger.
4. Put a typed nutrition domain command layer in front of the existing generic Google mutation machinery, including ownership, quantities, time, provenance, estimates, drafts, correction, and undo.
5. Build the text/manual path first, then adapters for photo, barcode, receipt, and voice into the same command pipeline.
6. Add model safety enforcement/evaluation and grounded answer provenance before calling the current `/ask` endpoint a coach.
7. Reconcile privacy/legal/store copy with durable server state and Workers AI processing before any user data reaches the Worker.
8. Add automated contract, ownership, security, safety, and cross-platform tests; then verify EAS/Worker deployments in staged environments.
